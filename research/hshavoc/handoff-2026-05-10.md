## Current Conclusions

- `$0585ba` is no longer the primary Plane B corruption suspect. Its compressed
  stream decompresses cleanly into coherent arcade graphics.
- The visible post-logo Plane B path is currently:
  `$08d134` decompression -> `$ff0010/$ff0180/$ff0640` -> `$039890` tilemap
  blitter -> Plane B VRAM at `$e000`.
- `EUTHERDRIVE_HSHAVOC_MCS_FORCE_H40=1` was a negative renderer probe: the
  framebuffer fingerprint did not change.
- `$fff906` is not a simple stuck wait flag. It is cleared each frame by
  `$000b1a` and then set again by scheduler/state-loop code such as `$018e00`.
- UI/adapter coin mapping exists:
  - UI maps arcade `Coin` to `mode`.
  - Insert Coin pulses `_coinPulseFrames`.
  - `McsArcadeAdapter` updates MAME ports so `:SYSTEM read=0x00fe` for coin and
    `:P1 read=0x007f` for start.
- Despite that, `hshavoc_state.io_r()` still reads unpressed values:
  - coin/system port `$06` reads `0x7f`
  - P1/start port `$02` reads `0x73`
- A driver-local `SetExternalInputState(start, coin)` pulse latch was added, but
  the current trace still shows `ext_start=0 ext_coin=0` at `io_r`. The next
  issue is likely the adapter-to-root reflection call or runtime ordering, not
  missing UI mapping.
