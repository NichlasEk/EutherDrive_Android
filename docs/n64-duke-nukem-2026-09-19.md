# Duke Nukem 64 (Europe): apparent stall and unreadable text

Baseline `65af7211`. Slot 1 source:
`/home/nichlas/roms/N64/Duke_Nukem_64__Europe_.z64_8aaa9cce.euthstate`.
Original SHA-256: `1692b767f629d666da3cb3f7e37e9f364ad2117f4e5a8f02cb8137975b0d6efd`.
The source is only read. Extraction verifies the embedded slot payload hash.
Artifacts: `.build-tmp/duke-2026-09-19/`.

## Findings and changes

The saved scene is not a halted CPU: the reference continues submitting roughly
three graphics tasks per wall-clock second. Start input progresses from the
legal screen to a Controller Pak message. Slow emulation and broken lettering
make the scene look frozen; this is not the Perfect Dark COP1 exception bug.

Duke's font uses combiner `fc30b26144664924`, computing
`(PRIMITIVE - SHADE) * TEXEL + SHADE` for RGB and alpha. Texture rectangles
incorrectly supplied opaque white as SHADE. With a white primitive color this
collapses to white regardless of the font texel, producing solid blocks.
Rectangles now supply zero shade, matching the zero shade coefficients in
[CEN64's RDP rectangle setup](https://github.com/n64dev/cen64/blob/e0641c8452a3ae8edcd2bf4e46794bb4eaafc076/rdp/n64video.c#L6914).
The same captured 6,949-command frame now renders readable copyright text.

Joybus also answered all four controller ports using the one input state and
one Controller Pak. The old run reports a pak on controller 4. Ports 2–4 now
report NoResponse and cannot read/write port 1's pak. Port 1 input and cartridge
EEPROM on channel 4 remain connected. RX error flags are cleared before each
new response, following the existing protocol behavior in
[Mupen64Plus PIF](https://github.com/mupen64plus/mupen64plus-core/blob/53a08fceb71653000dd6640cac05eb390fba7885/src/device/pif/pif.c#L66).
This reflects the currently implemented single-controller input API; it does
not add multiplayer input support.

## Validation

- 24 rectangle cases cover black/red/green/white, normal/flipped rectangles,
  one/two-cycle combiners and copy bypass.
- 21 controller cases cover presence, button/analog input, absent-port pak
  isolation, stale RX errors and continued parsing of the EEPROM channel.
- 18 EEPROM cases, 6,845 renderer/interrupt cases, 81 VI cases and snapshot
  checks pass. Snapshot checks require `EUTHERDRIVE_N64_PERF=1`.
- A 65-second resumed run with automated Start/A input reaches the logo screens
  and then **NEW GAME / LOAD GAME / OPTIONS**. See `fixed/frame-0055.png`.
  No unknown opcode is reported. This validates menu progression, not mission
  gameplay or a speedup; CPU/rendering costs still make the game slow.

```sh
dotnet tools/N64Probe/bin/Release/net8.0/N64Probe.dll --check-controller-ports
dotnet tools/N64Probe/bin/Release/net8.0/N64Probe.dll --check-rectangle-shade
dotnet tools/N64Probe/bin/Release/net8.0/N64Probe.dll --replay-rdp .build-tmp/duke-2026-09-19/capture .build-tmp/duke-2026-09-19/replay-new
```

The captured-frame equality check intentionally reports false after the shade
fix: the old white blocks are the bug, not the expected reference image.

A matching 65-second baseline run also reaches SELECT GAME TYPE, but with a
white background and damaged lettering (`reference-long/last.png`). Therefore
these changes fix presentation and false controller presence, not a proven
CPU hang. No claim of a new speedup or formerly unreachable gameplay is made.

Linux UI Release builds with zero errors (500 warnings). The app and tested
probe core match: `5ca0bc988ba20da8bcd72d562f4f6a616a57d13890b82d682b7b2ee506eac94b`.
The original user savestate SHA-256 remains unchanged.

A separate follow-up candidate: VI alternates between origins 0x680 and
0x25e80 later in the intro. The current probe skips framebuffer reads below
0x1000, so missing five-second captures must not be read as proof of a halt.
The core also contains low-address framebuffer heuristics; validate actual
presentation behavior before changing those bounds.
