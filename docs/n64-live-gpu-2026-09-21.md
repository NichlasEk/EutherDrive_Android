# Experimental live N64 Vulkan rendering on Linux

Resumed and tested on **2026-09-22**. The separate development launcher builds
and runs live Vulkan RDP rendering. The earlier
[pause checkpoint](n64-live-gpu-pause-2026-09-21.md) is retained as history.

The GPU backend now receives the running emulator's assembled RDP commands.
CPU, RSP, controller input, audio and interrupts continue running in Ryu64.
This is a separate opt-in desktop build; normal builds retain software RDP.
Mario reaches the castle from reset, accepts movement/jump input and swims
with coherent graphics. The measured complete run is still about 62% real
time, so this milestone does not establish full-speed gameplay or a win over
the normal software renderer. See the measurements and limits below.

## Run

From the repository root:

```sh
./scripts/run-n64-gpu-desktop.sh '/path/to/Super Mario 64.z64'
```

The launcher prepares the pinned native backend and builds the desktop into
`.build-tmp/n64-live-gpu/desktop`. It reuses the existing pinned checkout when
available; a clean workspace downloads the upstream checkout and submodules.
Requirements are Linux, .NET 8, CMake, Ninja, a C++17 compiler and a discrete
Vulkan GPU supporting the backend's coherent external host-memory import.
The validated host is the local RTX 4090. This is still a development build,
with shaders loaded from the upstream source directory.

`--build-only` prepares both binaries without launching a window. An explicit
`EUTHERDRIVE_N64_GPU_LIBRARY=/absolute/path/libeuther_n64_gpu.so` reuses a native
build. `N64_GPU_SOURCE` selects a prepared pinned checkout. Set
`EUTHERDRIVE_N64_GPU_VALIDATE=1` to require Khronos synchronization validation;
leave it off when measuring speed.

The frontend's **OpenGL** selector still describes how the window displays
pixels. The N64 RDP uses Vulkan underneath it. The deck monitor additionally
shows **N64 GPU** or **N64 software** in this build. The core's framebuffer status
reports `Vulkan RDP`, and performance diagnostics report commands, waits,
completed frames and validation errors.

Start from the ROM or Reset. GPU savestates are not implemented yet: saving
is rejected before touching a slot file. Loading an existing software save
joins the CPU, destroys the GPU context and resumes using software rendering.
Reset/reloading the ROM enables the GPU again. Stop, ROM changes and closing
the window explicitly stop the CPU before releasing native resources.

## Memory and presentation contract

- `N64LiveGpu=true` enables `N64_LIVE_GPU`. All MIPS memory, DMA and JIT hooks
  compile out of ordinary builds. Merely installing a shared library cannot
  enable the feature; the opt-in build also requires its explicit path.
- The first assembled RDP command creates the native device from current RAM.
  State commands still update software metadata, while rendering, texture
  loads and TLUT loads execute exclusively in the GPU backend.
- External CPU/JIT/DMA stores retain exact byte ownership, including writes
  of unchanged values. They are copied into an ordered immutable batch before
  the next RDP command. Partial stores never upload stale neighbouring bytes.
- The native batcher now also defers disjoint writes across ordinary 16-bit
  LoadBlock texture reads. Its narrow proof covers the source offset, width,
  transfer rounding and DXT permutation; other layouts retain their waits.
  Texture bytes written before a load still arrive before that load, while
  later CPU writes cannot change a preceding GPU read. See the
  [ABI contract](../native/N64Gpu/README.md) for the exact flag-16 restrictions.
- Pending color/depth writes have conservative address ranges bounded by the
  target width and scissor height, including word alignment and RAM wrap.
  Pages provide a fast rejection, followed by actual range overlap. CPU reads,
  generated JIT loads/code validation and DMA source reads wait when needed.
  Mario's depth buffer can begin at `0x400`, sharing a page with the exception
  vectors at `0x180`; a page match alone caused hundreds of unnecessary waits.
  The ordinary one-page read check stays small and inlinable. Thread identity
  and exact range enumeration live in a separate slow helper, reached only
  for a potentially overlapping or cross-page access.
- Synchronization submits the staged work, waits and reads back RAM, hidden
  memory and TMEM. GPU writes update existing memory epochs and code cache
  validation. FullSync completes before the existing DP interrupt is raised.
- Only FullSync publishes completed target snapshots. Presentation chooses
  the snapshot matching the VI origin/width/format, including its row offset,
  and holds the previous completed image while the next buffer is unfinished.
  SetColorImage and depth clears cannot publish intermediate images. The
  adapter uses the bridge's defined big-endian pixel order without guessing.
- A native failure is reported and stops that execution path. It never
  silently replays a partially executed frame through the software renderer.
  Stop waits for the CPU to leave native calls before destroying the device.

`EUTHERDRIVE_N64_GPU_AUDIT=1` independently checks live CPU RAM changes against
the recorded store masks at each synchronization. It also reports which
pending pages caused CPU waits. This is a diagnostic mode, not a timing mode.
Software journal capture and live GPU rendering are mutually exclusive.

## Validation and artifacts

Final-run artifacts are under `.build-tmp/n64-live-2026-09-22/`, outside version
control; the previous day's artifacts remain available for comparison.
The directed live checks compile both feature flags, but do not attach the
software journal observer:

```sh
dotnet build tools/N64Probe/N64Probe.csproj -c Release --no-restore -m:1 \
  -p:N64LiveGpu=true -p:N64RdpJournalCapture=true \
  -o "$PWD/.build-tmp/n64-live-checks/probe"

EUTHERDRIVE_N64_GPU_AUDIT=1 PARALLEL_RDP_SMALL_TYPES=1 \
  GRANITE_NUM_WORKER_THREADS=2 GRANITE_VULKAN_NO_VALIDATION=0 \
  taskset -c 6,7 dotnet .build-tmp/n64-live-checks/probe/N64Probe.dll \
  --check-live-gpu "$LIB" "$RESET_JOURNAL" "$ANGRYLION_REFERENCE"
```

The tests compare all RAM and hidden bytes at 20 Mario checkpoints against
the independent Angrylion reference through the actual live FIFO path. They
also exercise interpreter/JIT loads, mirrored reads, SP/general/AI DMA,
same-value and partial CPU stores, actual address-range boundaries, recycled
split command buffers, FullSync, completed VI presentation and rejected saves.
The separate `--check-live-gpu-lifecycle LIB ROM OUTPUT` test boots a real ROM,
stops and restarts it, checks a fresh GPU/memory pair, protects an existing
slot-file sentinel and loads a software save after native initialization.

Verified on the local RTX 4090 / Xeon E5-2697 v3:

- **44 live checks** with independent CPU-store auditing and Khronos
  synchronization validation, including generated JIT code overwritten by
  GPU output. All 20 Mario RAM/hidden checkpoints match Angrylion.
- **93 texture-ordering cases** compare complete RAM, hidden memory and TMEM
  to unbatched native execution and assert the expected barrier counts.
  These cover all tile slots, DXT extremes, rounded source boundaries,
  full-pixel S/T offsets, same-value stores and conservative fallback layouts.
- Native journal replay matches all RAM/hidden/TMEM bytes of independent
  Angrylion checkpoints: Mario 20, existing synthetic fixture 2, and
  color/depth/texture hazards 10. Mario's write barriers fall from 106 to 38
  with the new texture rule. These are startup checkpoints, not gameplay.
- Native ABI 68 checks and managed lifetime 13 checks pass. Real-ROM
  stop/restart, old-save software fallback and existing-save preservation pass.
- Normal CPU/JIT suite: 1,993 cases pass, including stale code, worker and
  reset behavior; RDP streaming 197 cases, audio and snapshot checks pass.
  Normal `Memory` retains 382 fields, 453 methods and 108,179 identical IL
  bytes relative to the accepted production baseline, with no journal members.
- The real desktop window boots and displays Mario in an isolated Xvfb
  session. Closing its actual MainWindow on the Avalonia dispatcher exits
  cleanly and detaches the GPU. Xvfb's OpenGL surface never renders, so the
  existing Bitmap fallback displays the frames; accelerated OpenGL window
  presentation is not established by this test. The first synthetic window
  manager close message was ineffective; the direct dispatcher close passes.

The final 180-poll GPU gameplay run reports over 3,400 FullSync frames, no
pending-frame read hazards and exits cleanly. Movement and swimming were
checked in the position/action telemetry and saved frames.
The final 200-poll run with both independent CPU-store auditing and Khronos
synchronization validation also reaches movement/swimming, passes over 3,200
FullSync frames and exits with zero untracked writes or validation errors.
Its runtime includes diagnostics and concurrent building, so it is not a
performance sample. Evidence: `mario-audit-final.log` and its frame captures.

## Measurements

A separate, controlled title-screen test leaves all controller buttons up
and compares the same guest-cycle interval, 1.2–1.8 billion cycles. Runs are
serial in the order old/new/new/old, pinned to cores 6/7, with identical audio
draining and no frame-capture poller. Linear interpolation of the one-second
telemetry brackets the interval; it contains about 6.33 s of emulated audio.
Initialization and the first billion guest cycles precede the measured window.

| Live GPU batching | Wall seconds for the same interval |
| --- | ---: |
| Draw ranges, run 1 | 23.970 |
| Texture reads, run 1 | 19.350 |
| Texture reads, run 2 | 19.326 |
| Draw ranges, run 2 | 23.585 |

The mean interval cost falls **18.67%**, equivalent to **22.96% more throughput**
in this title sequence. This compares two live GPU builds, not GPU against
software or a gameplay scene. The interval runs at approximately 26.4–26.8%
real time before the texture change and 32.7–32.8% after it. Full-ROM timing
and rendering-only timing are not interchangeable. `bench-title.py`,
`title-benchmark.json` and `title-benchmark-final.log` retain the setup/results.
The initial proposed later interval was not reached by the first 65-second
baseline run; the above interval was selected before timing either candidate,
and that completed baseline was reused.

A second interleaved experiment keeps texture batching enabled and separates
the CPU read check's cold synchronization code from its hot page rejection:

| CPU read check | Wall seconds for the same interval |
| --- | ---: |
| Original, run 1 | 19.277 |
| Small inlinable check, run 1 | 17.548 |
| Small inlinable check, run 2 | 17.785 |
| Original, run 2 | 19.630 |

Mean interval cost falls another **9.19%**, or **10.11% more throughput** in
this sequence. `title-read-benchmark.json` and `title-read-benchmark.log` retain
the results. All 44 ownership checks and real-ROM lifecycle checks were rerun
after this change and passed. These gains must not be multiplied into a
prediction of gameplay speed; gameplay is measured separately below.

The complete boot-to-game runs use the original USA ROM, cores 6/7, normal
.NET 8, audio draining, framebuffer capture, synchronous shader compilation
and no Vulkan validation/store audit. CPU input is scheduled by guest cycles
but polled once per wall-time loop, so trajectories diverge. These four
complete-run results are exploratory and must not be reported as a paired
gameplay speedup:

| Path | Wall seconds | Produced audio seconds | Audio / wall |
| --- | ---: | ---: | ---: |
| First live GPU, draw-range batching | 185.03 | 77.933 | 42.12% |
| Live GPU with texture-read batching | 187.55 | 111.451 | 59.42% |
| Final live GPU, including small CPU read check | 187.76 | 116.542 | 62.07% |
| Normal software renderer | 192.94 | 115.902 | 60.07% |

The GPU path's cumulative submit/wait/readback time drops from 71.02 s over
2,226 synchronizations to 25.00 s over 3,473 synchronizations in these runs.
That motivates the batching change, but different scene trajectories prevent
an exact before/after gameplay claim. Audio includes boot and cutscenes as
well as controlled movement; it is not an instantaneous in-game FPS counter.

Evidence: `gameplay-exploratory.json`, `mario-gpu-1.log`,
`mario-gpu-textures-1.log`, `mario-gpu-final.log`, `mario-software-1.log`; functional results in
`texture-checks.log`, `texture-ordering.log`, `live-textures.log`,
`*-textures-replay/`, `software-checks.log`, `snapshot-checks.log`,
`isolation-final.log`, and `desktop-smoke-final/`.

## Remaining work

Profile CPU/RSP execution and the bridge's remaining memory work in the live
GPU path before choosing the next broad speed change. The final comparison
still needs moving scenes with inputs applied deterministically at controller
reads, rather than through a wall-time poller. Preserve the software default
until a representative, repeatable gameplay win is demonstrated.

Full readback still copies 12 MiB plus TMEM per synchronization, even when only
a small framebuffer changed. Range-limited RDRAM readback and keeping hidden
memory/TMEM resident are the next transfer optimizations. They need independent
ownership tests before replacing this conservative path. Cold pipeline
compilation can stall a new scene.

Presentation currently uses completed raw color buffers, without the backend's
VI filters. GPU state export/import, five-game live compatibility coverage,
device-loss recovery, packaged shaders and distribution remain open. The
previous out-of-installed-RAM renderer discrepancy remains documented in
[the native checkpoint](n64-native-gpu-2026-09-21.md).
