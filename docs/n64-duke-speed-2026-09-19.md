# Duke Nukem 64: direct RAM doubleword reads

Baseline: `b99e82b1`. Artifacts: `.build-tmp/duke-speed-2026-09-19/`.
Resume source: `.build-tmp/duke-2026-09-19/fixed/state.bin` (Duke menu).

## Profile and change

A 20-second CPU sample of the resumed game attributes 28.93% of CPU-thread
samples to `ReadUInt64` and its callees. The old implementation allocates an
8-byte array and does nine memory-map lookups, then reverses the bytes.

`ReadUInt64` now reads directly from backing RAM when the address is in KSEG0
or KSEG1 and all eight bytes are inside installed RAM. It assembles the same
big-endian value without allocation. Device reads, TLB addresses, mirrored RAM
outside the backing array, and boundary-spanning accesses use the original
byte path. `ReadInt64` also benefits. No instruction timing, interrupts, writes,
frame skipping, or save format changes.

## Reproduction

`--check-read64` compares against the original byte-read path for 36,512
cases: both direct segments, signed/unsigned results, random data, unaligned
accesses, page crossings, installed-RAM end/mirroring and SP memory.

`--bench-cpu-state RAW_CPU_STATE ROM.z64` runs 20 million fetched instructions
with interrupt service and COP1 exceptions. Each process warms up three times,
then reports the median of five runs and a SHA-256 of the entire serialized
CPU/device/RAM state. The ROM must be big-endian. This is a deterministic game
CPU workload, not the full frontend or an FPS benchmark; it does not run the
CPU thread's outer loop shortcuts/history bookkeeping.

For the local scene, the raw state is extracted by removing the core wrapper:
version (int32), three uint32 fields, a BinaryReader-format string, two uint32
fields. Raw input SHA-256:
`e0228aa5aa8a79e6a0c41f42f2a10fc9f49055a8c3f76855fe9a19d8d5705ebe`.
Use the same newly built probe harness with the old/new `Ryu64.MIPS.dll` in
separate directories. Run sequentially pinned to CPU 6 in baseline/candidate/
candidate/baseline order, without concurrent builds or profiling.

```sh
dotnet tools/N64Probe/bin/Release/net8.0/N64Probe.dll --check-read64
taskset -c 6 dotnet tools/N64Probe/bin/Release/net8.0/N64Probe.dll \
  --bench-cpu-state .build-tmp/duke-speed-2026-09-19/cpu-state.bin \
  '/home/nichlas/roms/N64/Duke Nukem 64 (Europe).z64'
```

The earlier `bench-*.log` trial used a dummy ROM and is not the final game
measurement; only `rom-bench-*.log` uses actual cartridge data for DMA.

## Measured results

| 20 million instructions | First process median | Second process median |
| --- | ---: | ---: |
| Baseline | 2089.499 ms | 2286.051 ms |
| Candidate | 1480.056 ms | 1457.222 ms |

Averaging the process medians gives **32.9% less host time / 49.0% more
instruction throughput** for this workload. All four processes produce the
same full-state SHA-256:
`D0A31C5AB63AAA06E546D980031EF0AC2CB7A73B69AC10A215721B127565AE21`.
This is a menu workload; mission gameplay can have a different bottleneck.

Separate 30-second runs through the normal CPU thread (same state, real ROM,
CPU 6, first five seconds excluded) give:

| Menu run | Emulated cycles/host second | Graphics tasks/host second |
| --- | ---: | ---: |
| Baseline | 8.17 million | 2.59 |
| Candidate | 12.93 million | 4.06 |

These are headless menu measurements, not displayed FPS or mission gameplay.
Both runs report zero unknown opcodes. The live runs are sampled by wall time
and therefore finish at different emulated states; the fixed-work replay above
is the correctness comparison.

Validation: 36,512 read cases, 6,845 renderer/interrupt cases and 368 COP1 cases
pass. The mixed real-CPU-thread benchmark executes 10,000,001 instructions and
retains full-state hash
`41CBC873ED5B0FE3C41D49EBDC5166F7D6197F0A35B5EDA74670ABBCD86B0617`.

The mixed CPU workload (without LD) has medians 774.895 ms baseline and
786.605 ms candidate; no speed gain is claimed for that control workload.
Linux UI Release builds with 500 warnings and zero errors. Its core matches
the tested candidate SHA-256:
`4950e622ff59a9994a67e2eafc5f2001159246e5397f025be6d3234c2f8b2340`.
Original user slot-file SHA-256 remains unchanged:
`1692b767f629d666da3cb3f7e37e9f364ad2117f4e5a8f02cb8137975b0d6efd`.
