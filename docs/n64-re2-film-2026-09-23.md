# Resident Evil 2: publish decoded movie frames with the GPU core

The user's slot 2 reproduces a presentation failure, not a failed movie
decoder. The live GPU core now publishes the CPU/RSP-written movie buffers
at VI boundaries. The captured movie advances through different scenes;
the display previously remained on one black 320x230 image.

Artifacts: `.build-tmp/n64-re2-film-2026-09-23/`. The unmodified copied
container has SHA-256
`e5d19fa6e7d51f565fa51e02c1c14437f482fe2b1a8d8876fa973458f8dfdec9`.

`67f020192c34e4b735abb0c94a2fb6a0d64692df8adb2be59c90669c2830f5c0`.

## Reproduction

`before/` runs the frozen core from the preceding startup-fix pass for 30 wall
seconds from the copied slot. The CPU, RSP and audio continue; the RDP command
counter stays at 2,824,895. VI alternates between `0x0063e838` and `0x0076a838`,
with a width of 264 and a 32-bit pixel format. Direct RAM captures contain
different decoded movie scenes. The published frame is still the old black
320x230 snapshot. `before/presentation/frames.tsv` contains one unique image.

Previously only FULL_SYNC published GPU frame snapshots. This is suitable for
protecting unfinished RDP targets, but a movie writing scanout directly does
not submit new RDP commands. Consequently it never replaced that snapshot.

`before/comparison.png` shows the stale published image beside two decoded
RAM images. Its raw RAM captures deliberately use the probe's fixed 240-row
dump; bytes below the actual movie height are not a rendering oracle.
The programmed VI height for the movie is 136, and the corrected publication
uses **264x136 RGBA32**.

## Change

The emulation thread can now capture a CPU/RSP framebuffer on a VI origin
write and on a VI interrupt. It checks the programmed format and RAM bounds,
requires initialized backing pages, and compares with the latest matching
completed snapshot before allocating another image. Thus repeated polling or
unchanged VI fields do not publish duplicate CPU frames.

The UI still reads immutable copies. It never synchronizes the emulator's
GPU or reads a buffer while the CPU writes it. Publication is suppressed if
GPU writes, unfinished render targets, or a partial RDP command remain.
In particular, a CPU read hazard or save can reconcile GPU RAM before
FULL_SYNC; the outstanding render targets still block premature publication.

Normal byte/word stores and DMA already maintain serialized framebuffer page
epochs. Indexer/array stores, including the current SD implementation, do
not. A 256-byte page bitmap records those writes only on that path, preserving
same-value and all-black writes without adding bookkeeping to every fast
byte/word store. GPU memory save format 9 includes this bitmap; format 8 is
still accepted with an empty extra bitmap until subsequent indexer writes.
Existing ordinary write epochs and completed snapshots remain available on
those older saves. Core format 2, the UI container, and native GPU ABI do not
change. Software memory saves remain format 7.

There is no ROM-name, movie-address or game-specific production condition.
The native renderer and emulated instruction/event schedule are unchanged by
this presentation fix.

## Validation

- The new synthetic regression fails on the frozen previous core at its
  first CPU-only framebuffer publication.
- All **36 CPU-framebuffer checks** pass: RGBA16/RGBA32, direct and array
  stores, same-origin updates, immutable UI snapshots, RSP DMA, black frames,
  buffer swaps, register setup order, invalid/unwritten destinations, and
  complete save/restore continuation before the next field. They also verify
  an unfinished GPU draw stays hidden after a readback and a later CPU overlay
  replaces an older completed GPU snapshot.
- All **58 existing live GPU checks** pass, including independent Mario
  oracle frames, CPU/GPU ownership, JIT code invalidation, partial/same-value
  stores, DMA and completed-frame selection.
- All **six GPU savestate checks** pass with Vulkan validation and write
  auditing, with zero validation errors.
- RE2 boot save/load still has exact uninterrupted versus restored CPU,
  device, RAM, hidden-memory, TMEM, input, audio and image results.
- The same comparison now also starts from the user's **actual slot 2**:
  one guest second of warmup followed by uninterrupted and restored five-second
  movie continuations, with exact full state, audio, input and frames.
- A separate ten-guest-second before/after continuation preserves both
  checkpoints' cycles, input, audio hashes, RAM hashes and task counts, plus
  final RAM. The old published images stay black; the corrected 264x136
  images advance. `film-proof.json` records this intentional image difference.
- Mario's complete 90-guest-second sequence retains all 18 gameplay/audio/
  input checkpoints, all 18 sampled images and final RAM from the preceding
  startup-fix build. Only asynchronous JIT diagnostic counters vary.
- Normal and GPU Release desktop builds pass with zero errors. These are
  the final source changes, including the version 9 bitmap. No native GPU
  library change is needed for the film fix.
- `after/` captures advancing movie scenes for 30 wall seconds, with 405
  captured images in that diagnostic run. `after/comparison.png`
  collects representative scenes. This is a functional capture, not a speed
measurement or a claim about the movie's intended frame rate.

The gameplay-state checker accepts an optional initial core-state argument:

```sh
dotnet "$PROBE" --check-gpu-state-game "$ROM" "$OUTPUT" 1 "$CORE_STATE"
```

It requires a live-GPU performance-probe build and
`EUTHERDRIVE_N64_GPU_LIBRARY`. ROMs, user slots and derived movie captures
remain local; no ROM-derived data is added to Git.

The longer-term performance work is described in
[the agent plan](n64-realtime-agent-plan.md). This fix restores missing movie
images; it does not establish full-speed RE2 or complete game compatibility.
