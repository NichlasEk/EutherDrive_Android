# N64 CPU block compiler and performance direction

Baseline: `b1cc399f`. Target: Linux desktop N64 emulation. Local evidence and
candidate binaries are in `.build-tmp/n64-cpu-jit-2026-09-20/`.

## Why this change

The Rampage profile attributed about 24% of CPU samples to the bounded R4300
interpreter itself, before adding opcode dispatch, operand validation and
ordinary instruction handlers. Reducing a few timer checks cannot eliminate
that repeated interpretation work.

The new path compiles frequently encountered direct-RAM instruction sequences
into .NET IL and lets the runtime turn that into native code. Arithmetic uses
constant register indices and immediate operands; validated byte/halfword/word/doubleword loads
use direct RAM reads. SW uses the existing validated store helper, including
framebuffer dirtiness and RAM write epochs. Branches and ALU delay slots are emitted directly. Other delay-slot operations
and CP0 accesses retain the existing instruction helpers.

Compilation happens on one background worker at a time. The worker receives a
copy of the instruction words and cannot inspect or mutate live machine state.
Only a completed immutable delegate is published. Emulated CPU, RSP and device
execution keep their existing ordering.

## Correctness boundaries

- Code bytes are compared on every entry, including interior and delay-slot
  instructions. Cached code can survive a savestate restore without assuming
  that restored RAM matches the last execution.
- A store ends the compiled region, including stores in a terminal delay slot.
  The next instruction fetch observes the write before selecting another block.
- RAM bounds, alignment and direct-mapped address range are checked before a
  memory instruction. A failing check returns the already executed prefix and
  leaves the fault/MMIO instruction to the original interpreter.
- Compilation covers at most 16 instructions. A successful compiled entry can
  run within a quiet interval of up to 128 instructions, strictly before the
  next device, VI or CPU compare event. A cold entry falls back to the existing
  32-instruction interpreter budget.
- Store-free conditional backedges to the block start can repeat inside native
  code within the same quiet budget. Each iteration rechecks data addresses.
  CP0 operations exclude this path; partial exits and per-iteration history
  retain their original semantics. Code guards can be shared because neither
  the CPU block nor hardware can modify instruction memory during that interval.
- COUNT/RANDOM observations, branch-link ordering, r0 behavior, instruction
  history and self-branch watchdog cadence are preserved.
- Debug/trace/step modes retain the original batch restrictions. Compiled state
  is derived data and is not serialized. Cold power-on clears the caches.
- Cache limits are 8,192 address entries and 128 compiled versions. The
  conservative compilation cap prevents a long tail of rare blocks from
  continually consuming host CPU time. A full cache falls back to interpretation.
- `EUTHERDRIVE_N64_CPU_JIT=0` selects the interpreter fallback. Platforms that
  cannot generate dynamic code also fall back.

The core remains netstandard2.0. `System.Reflection.Emit.Lightweight` supplies
its dynamic-method API references; the desktop runtime executes the IL.

## Validation and measurement

The probe's `--check-cpu-jit` forces compilation for full-state comparisons
against ordinary instruction execution and checks instruction history too.
It includes active hardware timers, exact quiet-window boundaries, CP0 reads,
branch/link aliasing, self-modification, stale interior code and a cache reset
while a worker is compiling. Real game replays compare full serialized machine
state, including RAM, devices and RSP state.

The final compiler passes 883 full-state cases, including 737 cases that actually
execute compiled code. One million opcode classifications and 264,192 RANDOM
register cases pass. Worker tests cover stale code and replacing/resetting the
machine while a compilation is in flight. Release UI compilation succeeds.

Fixed-work replays requested 50 million guest instructions, with three warmups
and five measured samples per process. Processes ran serially on CPUs 6 and 7
(two distinct physical cores), without overlapping builds or our tests. Existing
user applications remained running. Hardware counters inherited child-thread
user-space work and were not multiplexed.

## Next architectural work

The existing OpenGL surface uploads and displays an already rendered image.
N64 RDP texture sampling, depth/coverage, combiner and blending work still runs
on the CPU in `Memory.cs`. OpenGL presentation therefore does not imply a GPU
RDP backend.

The next stages should follow measured bottlenecks:

1. Extend profitable CPU compilation coverage, including mapped code and more
   instructions, only with precise exceptions and event boundaries intact.
2. Improve RSP vector arithmetic/data layout inside its existing block compiler,
   using captured graphics/audio tasks and interpreter differential tests.
3. Specialize common RDP texture/combiner/blend modes once per draw rather than
   selecting every mode again for each pixel. Compare against the general path.
4. Evaluate a real GPU RDP backend as a separate project. Framebuffer readback,
   CPU-visible writes, depth, coverage and synchronization belong in its design.

No frame skipping, guest overclocking or reduced rendering accuracy is part of
this CPU work. Scene graphics-task rates are not display FPS or proof of full
speed. Short replays can overstate compilation costs; long scene runs must also
include startup and report the measurement interval.
